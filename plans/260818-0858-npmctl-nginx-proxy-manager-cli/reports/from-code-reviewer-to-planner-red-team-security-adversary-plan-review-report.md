# Red-Team Review — npmctl Plan (Security Adversary / Fact Checker)

Reviewer role: hostile security review + fact-check of NPM API and credential-handling claims.
Verification base: `https://github.com/NginxProxyManager/nginx-proxy-manager` tag `v2.15.1` (`backend/schema/**`, `backend/routes/**`, `backend/internal/**`, `backend/lib/**`).

## Finding 1: Plan's core API claim is false — a bounded long-lived token IS mintable, so D7's justification for persisting the plaintext admin password collapses

- **Severity:** Critical
- **Location:** `plan.md`:58 ("Corrections From Schema Verification"), `phase-01-core-foundation.md`:74 ("Auth: verified API shapes")
- **Flaw:** The plan states as verified fact: *"There is no `expiry` request parameter. Token lifetime is server-controlled"* and concludes *"The rejected 'mint a 1-year token' option was not implementable anyway."* That is wrong. It is true only for `POST /api/tokens` (which is schema-validated with `additionalProperties: false`). `GET /api/tokens` — the refresh endpoint the plan already depends on (`phase-01`:76) — accepts `?expiry=` and `?scope=` **with no schema validation at all**, and honors them.
- **Failure scenario:** The most security-relevant design decision in the plan (D7: store the admin password on disk forever, `plan.md`:48, `phase-01`:84) is justified by an incorrect API fact. The false claim is then propagated into implementation guidance (`phase-01`:74) and will be encoded in code comments and README. Nobody re-examines it, and npmctl ships persisting a reusable primary admin secret when it could have persisted a bounded credential. Note also that the brainstorm's *actual* rejection reason (`brainstorm…report.md`:77 "no token-revocation endpoint; leaked token = 1yr full admin") cuts against storing the password too: tokens are RS256-signed from `/data/keys.json` with **no DB token table**, so nothing revokes them — and changing the password does **not** invalidate outstanding tokens either. Storing the password gives an attacker permanent full admin *plus* web-UI login *plus* a likely-reused human secret; storing a 7–30d token gives strictly less.
- **Evidence:**
  - `backend/routes/tokens.js` — the GET route has **no** `apiValidator`: `internalToken.getFreshToken(res.locals.access, { expiry: typeof req.query.expiry !== "undefined" ? req.query.expiry : null, scope: ... })`. Contrast the POST route, which does call `apiValidator(getValidationSchema("/tokens","post"), req.body)`.
  - `backend/internal/token.js` `getFreshToken`: `thisData.expiry = thisData.expiry || "1d"` → `Token.create({ expiresIn: thisData.expiry })`.
  - `backend/lib/helpers.js` `parseDatePeriod`: `expression.match(/^([0-9]+)(y|Q|M|w|d|h|m|s|ms)$/m)` — `365d` and `1y` are accepted.
  - `backend/models/token.js` — header comment "*NOTE: This is not a database table*"; `jwt.sign(payload, getPrivateKey(), { algorithm: "RS256" })`. `backend/lib/config.js`:5 `const keysFile = '/data/keys.json'`. No revocation list exists.
- **Suggested fix:** Correct `plan.md`:58 and `phase-01`:74. Re-open D7 with the accurate options: (a) `auth login` mints a bounded token via `GET /api/tokens?expiry=30d` and stores **only** the token, discarding the password; (b) re-auth prompt when it lapses; (c) store the password only behind an explicit opt-in flag (`--store-password`) documented as "full permanent admin compromise if this file leaks, and NPM cannot revoke it." Also document that `npmctl auth logout` cannot revoke server-side (see Finding 5).

## Finding 2: `allowed-tools: Bash(npmctl:*)` plus "then re-run with `--yes`" pre-authorizes the entire NPM admin surface with one undifferentiated bit

- **Severity:** Critical
- **Location:** `phase-04-agent-skill-and-release.md`:53 (`SKILL.md` frontmatter), `phase-04`:64 (protocol rule 4), `phase-01-core-foundation.md`:119-126 (write gate behavior table)
- **Flaw:** The gate has exactly two states: refused, or `--yes`. `--yes` is a global flag with no scope, so the same token of consent that authorizes `host update --forward-port 8081` also authorizes `user set-password`, `user create --roles admin`, `user rm`, `user 2fa` (disable), `settings set`, and `user login-as`. Meanwhile `allowed-tools: Bash(npmctl:*)` tells the agent harness that *every* `npmctl` invocation is pre-approved, removing the human-in-the-loop tool-permission prompt that would otherwise be the real boundary. The skill then explicitly teaches the agent the `--yes` habit (`phase-04`:64 "**Only then** re-run with `--yes`").
- **Failure scenario:** A user asks the agent to "fix the 502 on app.example.com." The agent, following the trained loop (dry-run → show → `--yes`), has standing authority to run `npmctl user set-password --id 1 --secret …` or `npmctl user create --roles admin`. Verified: `PUT /users/{userID}/auth` requires only `type` and `secret` — the `current` password is **optional**, and security is `bearerAuth: ["admin"]`. So one pre-approved command silently takes over the NPM admin account (and locks the human out) with no separate consent step. A prompt-injected page title, a poisoned repo file, or plain model error is sufficient; no compromise of npmctl is needed.
- **Evidence:** `phase-04`:53 `allowed-tools: Bash(npmctl:*)`; `phase-04`:64 "**Only then** re-run with `--yes`"; `phase-03`:40 maps `user set-password` → `PUT /users/{id}/auth`; upstream `schema/paths/users/userID/auth/put.json` — `"required": ["type","secret"]`, `current` present but not required, `security: [{bearerAuth: ["admin"]}]`.
- **Suggested fix:** Split the gate into privilege tiers. Narrow the frontmatter to the read/host surface only (`Bash(npmctl host:*)`, `Bash(npmctl cert list:*)`, `Bash(npmctl audit-log:*)`, …) so admin/identity commands hit a human tool-approval prompt. Add a second, non-reusable gate for identity-class operations (`user *`, `settings set`, `auth *`): require `--i-understand=<resource>` typed confirmation, refuse them entirely when stdin is not a TTY, and add an opt-in `admin_commands_enabled: false` profile default. Add a `Guard` classification `Privileged` distinct from `Destructive`.

## Finding 3: `npmctl audit-log list` exfiltrates DNS provider API credentials in plaintext — straight into the agent's context window

- **Severity:** Critical
- **Location:** `phase-03-admin-resources.md`:76-78 ("Audit log"), `phase-03`:24 (`npmctl audit-log list|get`), `phase-04`:106 (troubleshooting recipe "find what changed")
- **Flaw:** The plan designates audit-log as *"the one admin endpoint with genuine agent value"* and wires it into skill recipes, with no redaction of the returned `meta` payload. Upstream, `meta` on audit rows contains full request/row payloads, and the **renew** path writes the certificate row into the audit log *without* the `dns_provider_credentials` omission that every other cert path applies. `GET /audit-log` returns `meta` verbatim.
- **Failure scenario:** User has a wildcard cert via DNS-01 with a Cloudflare API token in `meta.dns_provider_credentials`. Any `cert renew` (manual or via npmctl) persists that token into `audit_log.meta`. Later the agent runs `npmctl audit-log list --limit 10` to answer "what changed recently?" — the Cloudflare API token is printed to stdout, enters the model context, is written to the session transcript on disk, and is transmitted to the model provider. The user's DNS zone is now compromised, and nothing in npmctl logged or warned. The credential is also permanently in the NPM DB and in any backup.
- **Evidence:**
  - `backend/internal/certificate.js` `renew`: `const updatedCertificate = await certificateModel.query().patchAndFetchById(...)` then `internalAuditLog.add(access, { action:"renewed", ..., meta: updatedCertificate })` — **no** `utils.omitRow(omissions())`, unlike `create` which does apply it. `omissions()` at line 28 is `["is_deleted","owner.is_deleted","meta.dns_provider_credentials"]`.
  - `backend/internal/audit-log.js` `getAll` / `get`: rows returned raw; no `omitRow`, no meta filtering.
  - `phase-02`:66 confirms npmctl itself authors `dns_provider_credentials` into `meta`.
- **Suggested fix:** npmctl must redact on output, not trust the API. Add a mandatory output scrubber applied to every rendered payload (JSON, YAML, table, dry-run, verbose) that replaces values for a denylist of keys — `dns_provider_credentials`, `secret`, `current`, `token`, `challenge_token`, `certificate_key`, `privkey`, `password` — with `«redacted»`, plus a `--unsafe-show-secrets` escape hatch that refuses when stdout is not a TTY. Add a test asserting `audit-log list` output over a fixture containing `dns_provider_credentials` does not contain the value. Explicitly document that audit-log output may contain historical secrets.

## Finding 4: No redaction policy on dry-run output — the one path the skill mandates for every mutation prints secrets verbatim

- **Severity:** Critical
- **Location:** `phase-01-core-foundation.md`:123 (guard table, `--dry-run` row), `phase-01`:218 (success criteria), `phase-04`:62-63 (protocol rules 2-3)
- **Flaw:** The guard's dry-run behavior is *"print `METHOD /path` + pretty body"* — the **entire** request body, unfiltered. The only redaction requirement anywhere in the plan is `phase-01`:218, "Credentials absent from `-v` verbose output," which covers one output channel and (per `phase-01`:231) only the login password. Yet the skill instructs the agent to dry-run **every** mutation and **show the user the output** — meaning the highest-secret-density payloads are printed by design, on the happy path, into an LLM transcript.
- **Failure scenario:** `npmctl user set-password --id 1 --dry-run` prints `PUT /api/users/1/auth {"type":"password","secret":"<the new admin password>"}`. `npmctl cert create --dns-provider cloudflare --dry-run` prints the Cloudflare API token. `npmctl user create --dry-run` prints `auth.secret` (verified: `schema/paths/users/post.json` has an `auth` object with `{type, secret}`). All of it lands in stdout, shell scrollback, CI job logs, and the agent transcript. The agent then does exactly what it was told and pastes the dry-run output back to the user in chat. No test in any phase would catch this.
- **Evidence:** `phase-01`:123 "print `METHOD /path` + pretty body"; `phase-01`:218 "Credentials absent from `-v` verbose output (test greps captured log)" — scoped to `-v` only; `phase-04`:63 "**Show the user** the dry-run output"; `phase-03`:40 `user set-password` → `PUT /users/{id}/auth`; upstream `schema/paths/users/post.json` `properties.auth` example `{"type":"password","secret":"bigredhorsebanana"}`.
- **Suggested fix:** Route dry-run, verbose, and error rendering through the same scrubber from Finding 3 — redaction must be a property of the serializer, not of individual call sites. Also redact the `Authorization: Bearer …` header in `-v` (a bearer JWT is an unrevocable credential — see Finding 5; `phase-01`:218 as written does not require this). Extend the success criterion to a table-driven test over every command that carries a secret-bearing field.

## Finding 5: The write gate and the credential live in the same trust domain — Guard cannot constrain a caller that holds the password, and `auth logout` revokes nothing

- **Severity:** High
- **Location:** `phase-01-core-foundation.md`:84 (chain step 4), `phase-01`:91 ("Plaintext 0600 is deliberate"), `phase-01`:104 ("hard invariant; a test enforces it"), `phase-01`:228 (R4 mitigation "Guard is the single chokepoint")
- **Flaw:** R4 is stated as "agent misuse on production," mitigated by "Guard is the single chokepoint; test asserts no command bypasses it." That invariant is enforced by a **Go unit test over in-repo call sites** — it constrains npmctl's own source, not the agent. The agent runs as the same user, and the plan hands it a world-readable-to-that-user plaintext admin password (`~/.config/npmctl/credentials.json`) or an unlocked keyring. `curl -d '{"identity":…,"secret":…}' …/api/tokens` then `curl -X DELETE …/api/nginx/proxy-hosts/12` bypasses Guard entirely, in two commands, with no npmctl involvement. A safety gate placed *inside* a binary cannot constrain a principal that possesses the underlying credential.
- **Failure scenario:** Agent is asked to "clean up unused hosts," Guard refuses with exit 3, and the agent — reasoning around an obstacle exactly as models do — reads `~/.config/npmctl/credentials.json` and calls the API directly. Skill rule 6 (`phase-04`:66) forbids "retry with different flags"; it says nothing about not using the credential directly. Post-incident there is also no recovery: exfiltrated JWTs cannot be revoked (no token table; RS256 keys in `/data/keys.json`), and rotating the admin password does **not** invalidate outstanding tokens. `npmctl auth logout` (`phase-01`:22) can only delete local state, yet the plan never says so — a user who believes they "logged out" after a suspected leak is wrong.
- **Evidence:** `phase-01`:104 "No command calls a write method on the client directly. This is a hard invariant; a test enforces it"; `phase-01`:228; `phase-01`:84; upstream `backend/models/token.js` ("*this is not a database table*", `jwt.sign` with `getPrivateKey()`), `backend/lib/config.js`:5 `keysFile = '/data/keys.json'`, `backend/internal/token.js` (password verification and token signing are independent — `auth.verifyPassword` gates issuance only).
- **Suggested fix:** State the threat model honestly in `plan.md`: Guard protects against *accidental* mutation, not a hostile or prompt-injected agent; the actual boundary is credential possession. Then move real enforcement to where it holds: a low-privilege NPM user for the agent profile (NPM has per-resource permissions — `PUT /users/{id}/permissions`, and PUT proxy-hosts is scoped `proxy_hosts.manage`) so a bypass is bounded by server-side authorization. Also correct `phase-01`:91: `gh`, `docker login`, and `kubectl` store **tokens/certs** — revocable, scoped, non-reusable artifacts — not the account's primary password. The analogy is doing load-bearing work and it is false. Document that `auth logout` is local-only and that NPM has no revocation path.

## Finding 6: The credential chain is not profile-scoped, so `-p lab` (with `insecure_skip_verify: true`) can send the production admin password to an attacker

- **Severity:** High
- **Location:** `phase-01-core-foundation.md`:78-85 ("Credential resolution chain"), `phase-01`:162-173 (config example), `phase-01`:196 (step 8), `phase-01`:156-158 (R3)
- **Flaw:** Profiles are a first-class concept for `url` and `insecure_skip_verify`, but the credential chain has **no profile dimension**: `NPMCTL_TOKEN` / `NPMCTL_PASSWORD` are single global variables, and neither the keyring key nor `credentials.json` is described as keyed by profile. `phase-01`:196 scopes profile resolution to config only. The shipped example then shows two profiles with the **same `identity`**, one with TLS verification disabled.
- **Failure scenario:** Developer exports `NPMCTL_PASSWORD` for `prod` in their shell (or CI). They run `npmctl -p lab host list`. npmctl resolves the same global password and sends it to `https://10.0.0.5:81` with `insecure_skip_verify: true` — no certificate validation. Anyone who can answer on that address (ARP/DNS spoof on a homelab LAN, a stale DHCP lease, a compromised container) receives the **production admin password in cleartext-to-them TLS**. Because auth is password-based rather than token-based, MITM yields a permanent credential, not a 1-day token — and per Finding 5 there is no revocation. `insecure_skip_verify` is persisted silently in config (`phase-01`:172), so the warning, if any, is shown once at setup and never again.
- **Evidence:** `phase-01`:80-85 (chain lists `NPMCTL_TOKEN / NPMCTL_PASSWORD` with no profile qualifier); `phase-01`:167-173 (`prod` and `lab` both `identity: me@example.com`, `lab` has `insecure_skip_verify: true`); `phase-01`:196 "resolve profile ← flag ← env ← default" — config only; `phase-01`:157 "Default **off**" with no per-invocation warning requirement.
- **Suggested fix:** Namespace every credential by `(profile, url, identity)` — keyring service `npmctl:<profile>`, and a per-profile map in `credentials.json`; refuse to use a stored credential if the profile's `url` or `identity` changed since it was stored (URL rebinding = re-auth). Support `NPMCTL_PASSWORD_<PROFILE>` and require `NPMCTL_PROFILE` for the unsuffixed form. When `insecure_skip_verify` is active, print a warning to stderr on **every** invocation, log the presented cert fingerprint, and refuse to send a *password* over an unverified connection at all (token-only). Add `--ca-cert` and `--pin-sha256` so the R3 use case is served without disabling verification — the plan offers no alternative and jumps straight to "unusable without it."

## Finding 7: `user login-as` mitigation is "printed only" — for an AI-driven CLI, printing *is* the leak

- **Severity:** High
- **Location:** `phase-03-admin-resources.md`:53 ("Never write the returned token to the credential store. Print it, or require `--json`"), `phase-03`:120 (risk row "token leakage → Classified destructive, never persisted, printed only")
- **Flaw:** The stated mitigation for impersonation-token leakage is "not persisted, printed only." This models the threat as *disk* exposure while ignoring that in this tool's primary use case stdout **is** an exfiltration channel: it goes into the agent's context, the on-disk session transcript, and the model provider. Calling it "destructive → requires `--yes`" also does not help, because the skill trains `--yes` (Finding 2).
- **Failure scenario:** Agent runs `npmctl user login-as 2 --yes` while investigating a user's host visibility. The response — verified schema `required: ["expires","token","user"]` — puts a valid JWT for user 2 plus that user's email, name, nickname, and roles into the transcript. Default lifetime is 1 day (`verify2FA`/`getFreshToken`: `expiry || "1d"`), and it is **unrevocable** (Finding 5). Anyone who later reads the transcript — a log aggregator, a shared CI artifact, a compromised laptop — has a working NPM session for 24h and the user's PII. No `--yes` prompt makes that visible, because the token appears *after* the confirmation.
- **Evidence:** `phase-03`:53; `phase-03`:120; upstream `schema/paths/users/userID/login/post.json` — response requires `expires`, `token`, `user` (with `user-object.json`: email, name, nickname, avatar, roles), `security: [{bearerAuth: ["admin"]}]`.
- **Suggested fix:** Default to **not** printing the token: print only `expires` and the impersonated identity, and write the token to a file with mode `0600` at a caller-specified path (`--token-out`), or to fd 3. Require `--print-token` (refused when stdout is not a TTY) to emit it inline. Redact the `user` object to id + email. Ban `login-as` from the skill's allowed-tools list and say so in `SKILL.md`. Note in the plan that the token cannot be revoked, so the only containment is waiting out `expires`.

## Finding 8: `cert download` writes TLS private keys into the current working directory with unspecified permissions, and `-` streams them to stdout

- **Severity:** High
- **Location:** `phase-02-host-resources.md`:80-82 ("`cert download`"), `phase-02`:23 (`cert … download`), `phase-02`:118-119 (success criteria)
- **Flaw:** The plan treats `cert download` purely as an output-formatting problem ("Returns a file, not JSON… never corrupts stdout"). It never states what the file *contains*. Verified upstream: the endpoint returns a zip of **every** `.pem` in the live cert directory — which includes `privkey.pem`. The plan specifies "default cwd," no file mode, no overwrite policy, and explicitly allows `-` to stream to stdout.
- **Failure scenario:** Agent runs `npmctl cert download 3` from inside the user's git repo (cwd = repo root). A zip containing the site's TLS private key is written with default umask (commonly `0644`), unignored by `.gitignore` (nothing in `phase-01`:185 anticipates it), and is committed and pushed on the next `git add -A`. The private key is now in a remote repository and in git history permanently. Variant: an agent asked to "show me the cert" uses `-`, dumping binary key material into the transcript.
- **Evidence:** `phase-02`:81 "Write to `--output-dir` (default cwd), never to stdout unless `-` is given explicitly"; upstream `schema/paths/nginx/certificates/certID/download/get.json` → `content: application/zip`; `backend/internal/certificate.js` `download`: `fs.readdirSync(zipDirectory).filter((fn) => fn.endsWith(".pem"))` → `zipFiles(certFiles, opName)` (the live dir contains `privkey.pem`, written at line ~521 as `privkey.pem`).
- **Suggested fix:** Treat the download as key material: create the file with mode `0600`, default the destination to `$XDG_DATA_HOME/npmctl/certs/` (never cwd), refuse to overwrite without `--force`, refuse `-` entirely unless `--unsafe-stdout` is passed and stdout is not a TTY-less pipe into an agent, and print the destination path plus a "contains a private key" warning to stderr. Add `*.zip`/`*.pem` to the generated `.gitignore`. Add a success criterion asserting the 0600 mode.

## Finding 9: `advanced_config` — a raw-nginx injection sink that escalates "manage proxy hosts" to full NPM compromise — appears nowhere in the plan

- **Severity:** High
- **Location:** absent from all four phase files (`grep -rni advanced_config` over the plan directory returns zero hits); implicitly in scope via `phase-01`:200 (`proxyhosts.go … Create/Update`) and `phase-01`:151-153 (the update builder)
- **Flaw:** `advanced_config` is a free-form string on proxy hosts (and per-`location`) that NPM splices verbatim into the generated nginx server block. It is the single highest-privilege field in the entire API, and the plan gives it no distinct handling: no mention, no warning, no separate gate, no diff rendering rules. It is treated as interchangeable with `forward_port`. The update builder pattern (`phase-01`:151) will expose it as just another `SetX`.
- **Failure scenario:** A prompt-injected or merely wrong agent issues `npmctl host update 12 --advanced-config 'location /x { alias /data/; autoindex on; }' --yes`. It passes `nginx -t` (it is valid nginx), so NPM loads it and reloads (`internal/nginx.js` `configure` only rolls back on a **test failure**). NPM's `/data` volume is now served over HTTP: `database.sqlite` (all users, bcrypt hashes, all cert metadata including DNS credentials) and `keys.json` — the **RSA private key that signs every NPM token**. With `keys.json` the attacker forges admin tokens indefinitely; rotating the password does not help (Finding 5), and no NPM API call can rotate that key. Secondary: `proxy_pass` to internal-only addresses turns the public proxy into an SSRF pivot; a multi-line config in a dry-run diff is trivially skimmed past by a human clicking through the `--yes` loop (`phase-04`:63-64).
- **Evidence:** plan grep: zero occurrences of `advanced_config`. Upstream `schema/paths/nginx/proxy-hosts/hostID/put.json` accepts `advanced_config` and `locations`; `schema/components/proxy-host-object.json` — `"advanced_config": { "type": "string", "example": "" }` (no pattern, no maxLength) and `locations[].advanced_config: {"type":"string"}`; `backend/internal/nginx.js` `configure` → `generateConfig` → `test()`, rolling back **only** when `nginx -t` fails; `backend/lib/config.js`:5 `keysFile = '/data/keys.json'`.
- **Suggested fix:** Add `advanced_config` (host-level and per-location) to the plan as a named risk. Classify any mutation touching it as its own gate tier: require `--yes` **plus** `--allow-advanced-config`, render it as a full line-by-line diff (not a JSON blob) in dry-run, and refuse it entirely when stdin is not a TTY unless the extra flag is present. Exclude it from the skill's documented vocabulary and add an explicit `SKILL.md` prohibition. Optionally screen for high-risk directives (`alias`, `root`, `include`, `access_log`, `error_log`, `perl`, `lua`, `proxy_pass` to RFC1918) and warn.

## Finding 10: Exit code 4 collapses "wrong password," "2FA required," and "account disabled" into one value, while auto-relogin turns any of them into an unbounded credential-replay loop

- **Severity:** Medium
- **Location:** `phase-01-core-foundation.md`:94-100 ("Session lifecycle"), `phase-01`:137 (exit code 4), `phase-04`:66 (protocol rule 6)
- **Flaw:** Every mutating invocation runs `refresh fails / 401 → re-login from stored password`. The exit-code contract offers a single `4` for all auth outcomes, and skill rule 6 restrains the agent only on exit **3** — nothing tells it to stop on repeated 4s. So the "unattended agent" property is implemented as: replay the stored admin password on every failure, forever, with the agent free to retry.
- **Failure scenario:** An admin rotates the NPM password (or enables 2FA, or the account is disabled). Every subsequent npmctl call now performs a fresh `POST /api/tokens` with the stale password. An agent in a retry loop, or a cron/CI wrapper, generates hundreds of failed admin logins against a production instance. Upstream `internal/token.js` returns the same `AuthError("Invalid email or password")` for unknown user, missing auth row, and bad password, with **no delay and no lockout** — so npmctl becomes a convenient password-spraying client against its own instance, and the operator has no signal distinguishing "my password changed" from "someone is attacking me." Separately, if 2FA was enabled after login, `POST /api/tokens` returns a *200* with a `{requires_2fa, challenge_token}` challenge — not an error — so a client that assumes 200 means success will fail confusingly rather than reporting "2FA required." The plan handles the `oneOf` at login (`phase-01`:72) but the auto-relogin path (`phase-01`:98) is described only as "re-login from stored password," with no mention that unattended re-login is impossible once 2FA is on.
- **Evidence:** `phase-01`:98 "refresh fails / 401 → re-login from stored password"; `phase-01`:137 `| 4 | auth failure |`; `phase-04`:66 (rule 6 covers exit 3 only); upstream `backend/internal/token.js` — three separate paths all `throw new errs.AuthError(ERROR_MESSAGE_INVALID_AUTH)`, no throttle; `has2FA` branch returns `{requires_2fa: true, challenge_token}` with HTTP 200 (`schema/paths/tokens/post.json` `oneOf` → `token-challenge.json`, `required: ["requires_2fa","challenge_token"]`).
- **Suggested fix:** Attempt at most one re-login per process, and record a local failure counter — after N consecutive auth failures, refuse to send the password again until the user runs `npmctl auth login` interactively (prevents both spraying and lockout amplification). Split the contract: `4` = credentials rejected (stop, do not retry), and add a distinct code for "interactive re-auth required (2FA / challenge)" so an agent can surface it instead of looping. Extend skill rule 6 to cover it: refusal *and* auth failures are terminal, never retried. Add the "wrong password vs. attack is indistinguishable" caveat to the plan's risk table.

## Additional fact-check notes (not numbered findings)

- **"All 44 endpoints" is a path count, not an operation count.** `swagger.json` has **44 unique paths** but **68 method+path operations**. `phase-03`:103 makes the acceptance criterion *"verified against the vendored schema's **path list**"* — that gate passes even if an entire method (e.g. `PUT /nginx/access-lists/{listID}`) is unimplemented. Also `GET /` (the root/health operation, `paths/get.json`) is not mapped in any phase's command table; `phase-01`:23 maps `version` to `/version/check` only. Parity claim as written is 43/44 paths. Fix: make the checklist operation-level (method+path), and reconcile the "44" figure in `plan.md`:19 and `plan.md`:44 with the 68 operations actually being wrapped.
- **`PUT` "has no required fields" is imprecise.** `plan.md`:60 and `phase-01`:143 are right that there is no `required` array, but `paths/nginx/proxy-hosts/hostID/put.json` sets `"minProperties": 1` with `requestBody.required: true` — an empty-body PUT is rejected. Also `additionalProperties: false`, so the map-based builder (`phase-01`:151) must never emit an unknown key or the request 400s.
- **The R1 partial-update assumption is confirmed by implementation, not by the schema.** `backend/internal/proxy-host.js` `update` does `.patch(thisData)`, so omitted `meta` is genuinely untouched — R1's mitigation is sound. Worth recording *where* that was verified, since the schema alone does not guarantee it and a future NPM release could change it (a case `schema check` would **not** catch — it is a behavioral, not structural, contract).
- **`DELETE /users/{userID}/2fa` takes the TOTP code as a query parameter** (`schema/paths/users/userID/2fa/delete.json`, `in: "query", name: "code", required: true`). Disabling another user's MFA is a security-control downgrade, yet `phase-03`:41/118 treats the 2FA group as an untyped "thin passthrough" and `phase-03`:87/97 classifies only `login-as` as destructive. Also, a code in a URL lands in NPM's access log and in npmctl's `-v` output. Classify 2FA-disable as privileged (Finding 2) and scrub query strings in verbose logging.

## Unresolved questions

1. Will D7 be re-opened now that `GET /api/tokens?expiry=` is confirmed usable, or is persisting the admin password an accepted user decision? (It changes the blast radius of every other finding here.)
2. Is the agent expected to operate as the NPM **admin**, or can a scoped NPM user be provisioned for it? Server-side authorization is the only bypass-proof control available (Finding 5).
3. Should `user *`, `settings set`, and `login-as` ship in v1 at all? They exist solely to satisfy D3 (full parity), which `phase-03`:16 already concedes is "low daily value" — while contributing most of the attack surface in this report.
