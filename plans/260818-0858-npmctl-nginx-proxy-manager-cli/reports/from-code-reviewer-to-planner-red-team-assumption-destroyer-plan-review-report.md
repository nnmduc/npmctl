## Finding 1: R1 — the plan's only Critical risk is aimed at the wrong object; proxy-host `meta` has nothing to do with Let's Encrypt renewal

- **Severity:** Critical
- **Location:** `plan.md:66` (risk table R1), `phase-01-core-foundation.md:143` section "R1 — the `meta` trap"; propagated to `plan.md:60`, `plan.md:80`, `phase-01:145–154`, `phase-01:215`, `phase-01:226`, `phase-02-host-resources.md:100`, `phase-02:119`, `phase-02:128`
- **Flaw:** `phase-01:143` asserts proxy-host `meta` "is a writable free-form object holding Let's Encrypt state (`letsencrypt_agree`, `dns_challenge`, `dns_provider_credentials`)". It is not the renewal source of truth. Let's Encrypt renewal is driven entirely off the **certificate** table, and the API exposes **no** write path to certificate `meta` other than create/upload. `npmctl` cannot break renewal via `host update` at all.
- **Failure scenario:** Not a production outage — a planning outage. A Critical-rated risk consumes a bespoke builder type (`ProxyHostUpdate` with `fields map[string]any`), a P1 regression test, and an "extend to every resource with an update path" mandate in P2 (`phase-02:128`) to protect a field whose only real contents are `nginx_online` / `nginx_err`, which the server **regenerates on the very next update** (`internal/nginx.js` `configure()` patches `meta: _.assign({}, host.meta, {nginx_online, nginx_err})` after every host write). Meanwhile the genuinely irreversible operation in the whole surface — `cert rm`, which calls `internalCertificate.revokeLetsEncryptSsl(row)` and **revokes the certificate at Let's Encrypt** (`internal/certificate.js` delete path) — is not risk-ranked anywhere, and `phase-02:41` treats it as an ordinary DELETE.
- **Evidence:**
  - `backend/schema/components/proxy-host-object.json` → `properties.meta` is exactly `{"type":"object","example":{"nginx_online":true,"nginx_err":null}}`. No LE fields, no sub-properties.
  - `backend/internal/certificate.js` → `processExpiringHosts()` queries `certificateModel.query().where("is_deleted",0).andWhere("provider","letsencrypt").andWhere("expires_on","<",expirationThreshold)` and calls `internalCertificate.renew()` per certificate. Proxy hosts are never read.
  - Renewal credentials come from the **certificate** row: `fs.writeFileSync(credentialsLocation, certificate.meta.dns_provider_credentials, {mode: 0o600})`.
  - `swagger.json` `paths` contains no `PUT /nginx/certificates/{certID}` — only `GET`/`POST` on the collection, `GET`/`DELETE` on `{certID}`, plus `renew`/`upload`/`download`. There is no npmctl-reachable write to certificate `meta`.
  - The residual real (minor) failure mode the plan never states: `internal/proxy-host.js` update reads `meta: _.assign({}, row.meta, thisData.meta)` **only** when `certificate_id === "new"`. So wiping host meta degrades a *future* quick-cert request, not renewal.
- **Suggested fix:** Re-rate R1 from Critical to Low/Medium and restate the actual failure mode. Promote the real Critical: `cert rm` revokes at Let's Encrypt and is irreversible — it needs its own confirmation class (name-echo, not just `--yes`), and `--dry-run` must state "this will REVOKE the certificate at Let's Encrypt". Keep the meta-omission rule (it is cheap and correct); drop the mandate to replicate the regression test across every resource.

## Finding 2: "PUT has no required fields, omitted fields are left untouched" is correct by accident; the real server behaviour makes `--dry-run` a false preview

- **Severity:** High
- **Location:** `plan.md:60` ("Corrections From Schema Verification"), `phase-01:143`, `phase-01:123` (Guard dry-run row), `phase-04-agent-skill-and-release.md:61–64` (protocol rules 2–4)
- **Flaw:** The plan derives a runtime behaviour ("omitted fields left untouched") from a schema property ("no `required`"). Those are unrelated. The claim happens to hold, but for a reason the plan never saw — and that same reason silently rewrites fields the caller did not send, which the plan's dry-run cannot show.
- **Failure scenario:** `npmctl host update 12 --certificate-id 0 --dry-run` prints `PUT /api/nginx/proxy-hosts/12 {"certificate_id":0}`. The agent shows the user that diff (`phase-04:63` rule 3: "Show the user … what will change"), the user approves, and the server additionally sets `ssl_forced=false`, `http2_support=false`, `hsts_enabled=false`, `hsts_subdomains=false`. HTTP/2 and HSTS are silently switched off on a production host and the dry-run said nothing. Second scenario: an update builder that emits only `{"advanced_config":"…"}` is fine, but any builder emitting an empty map gets HTTP 400 (`minProperties: 1`), not a no-op; and a `map[string]any` builder that ever emits a key outside the whitelist gets 400 (`additionalProperties: false`) — including the read-only fields (`id`, `modified_on`, `owner`, `certificate`, `access_list`) that a naive GET-merge-PUT would round-trip.
- **Evidence:**
  - `backend/schema/paths/nginx/proxy-hosts/hostID/put.json` → request body `"additionalProperties": false, "minProperties": 1` and an explicit 19-key whitelist. There is no `required` array — schema-optional, as the plan says — but `minProperties: 1` and the closed whitelist are both unmentioned in the plan.
  - `backend/internal/proxy-host.js` `update()` → `thisData = internalHost.cleanSslHstsData(thisData, row); … .patch(thisData)`.
  - `backend/internal/host.js` `cleanSslHstsData(data, existingData)` → `const combinedData = _.assign({}, existingData || {}, data); if (!combinedData.certificate_id) { combinedData.ssl_forced = false; combinedData.http2_support = false; } if (!combinedData.ssl_forced) { combinedData.hsts_enabled = false; } if (!combinedData.hsts_enabled) { combinedData.hsts_subdomains = false; } return combinedData;`
  - So the server itself performs GET-merge-PATCH with the full existing row, plus coercion. "Omitted = untouched" is an emergent property of an undocumented implementation detail, not an API contract.
- **Suggested fix:** (a) Restate `plan.md:60` as "the server merges the existing row before patching (`cleanSslHstsData`), so omitted fields survive — this is implementation behaviour, not a schema guarantee; `schema check` will not detect it changing." (b) Whitelist the builder's emittable keys against the PUT schema and reject empty payloads client-side with exit 2. (c) After every successful write, diff the returned object against the requested payload and print any server-coerced field to stderr; add this to the P1 success criteria. Otherwise `phase-04:63` rule 3 is a promise the tool cannot keep.

## Finding 3: Auto-relogin (D7) is impossible on a 2FA-enabled account; the plan specifies neither the challenge shape, its 5-minute window, nor the non-TTY failure path

- **Severity:** Critical
- **Location:** `phase-01:95–100` ("Session lifecycle"), `phase-01:69–76` ("Auth: verified API shapes"), `phase-01:207` and `phase-01:210` (success criteria), `plan.md:48` (D7 "auto-relogin"), `plan.md:76` (AC1: "call 48h later works with no re-prompt"), `plan.md:57`
- **Flaw:** The session design terminates every failure path in "re-login from stored password". On a 2FA account that yields a *challenge*, never a token. No stored secret can produce a TOTP code. The plan says "login must branch on this and call `POST /api/tokens/2fa`" (`plan.md:57`) without stating where the 6–8 digit code comes from in an unattended agent context — which is the entire point of D7. `phase-01:207` reduces this to "2FA challenge response path handled (unit test with fixture)": a fixture test proves JSON unmarshalling, not that the flow is reachable.
- **Failure scenario:** Production NPM admin has 2FA on (recommended, and NPM ships it). Token lifetime is hardcoded `"1d"`. Day 1 the operator runs `npmctl auth login`, types a code, everything works. Day 2 an agent runs `npmctl host list` in a non-TTY session; the cached token is expired; `GET /tokens` returns 401; auto-relogin posts identity+secret and receives `{"requires_2fa":true,"challenge_token":"…"}`. The plan's code has no branch for this in the *refresh* path (only in interactive login), so it either misparses the response as a token object and sends `Bearer undefined`, or falls through to a generic error. AC1 (`plan.md:76`, "48h later works with no re-prompt") is unachievable on a 2FA account by construction. Additionally, the challenge token lives **5 minutes** — an agent that prompts the user and waits gets "Invalid or expired challenge token" with no indication that re-login is required from the start.
- **Evidence:**
  - `backend/internal/token.js` `getTokenFromEmail()` → `if (has2FA) { const challengeToken = await Token.create({ …, scope: ["2fa-challenge"], expiresIn: "5m" }); return { requires_2fa: true, challenge_token: challengeToken.token }; }`
  - `backend/schema/paths/tokens/2fa/post.json` → body `required: ["challenge_token","code"]`, `additionalProperties:false`, `code` is `type: string, minLength: 6, maxLength: 8`. (Note: **string**, not integer — a leading-zero TOTP code marshalled as an int is a guaranteed 400.)
  - `backend/internal/token.js` — `data.expiry = data.expiry || "1d"` and `thisData.expiry = thisData.expiry || "1d"`: default token lifetime is 24h in both mint and refresh.
  - `verify2FA()` rejects with `AuthError("Invalid or expired challenge token")` once the 5m window closes.
- **Suggested fix:** Add an explicit contract to `phase-01`: (a) the refresh/re-login path must detect `requires_2fa` and, when stdin is not a TTY, exit 4 with the message "account has 2FA enabled; unattended re-authentication is not possible — run `npmctl auth login` interactively or use `NPMCTL_TOKEN`"; (b) document `code` as a string and preserve leading zeros; (c) document the 5-minute challenge window and re-request the challenge rather than reusing a stale one; (d) qualify AC1 as "non-2FA account, or `NPMCTL_TOKEN` supplied"; (e) add a `SKILL.md` rule for 2FA accounts. See also Finding 4 — long-lived tokens are a real alternative here.

## Finding 4: "There is no `expiry` request parameter … the 1-year-token option was not implementable anyway" is false — `GET /api/tokens` accepts undocumented `expiry` and `scope` query params. D7 rests on a wrong fact.

- **Severity:** High
- **Location:** `plan.md:58` ("Corrections From Schema Verification" item 2), `phase-01:74` ("**There is no expiry request parameter.** Lifetime is server-controlled"), `plan.md:48` (D7 "password stored"), `phase-01:78–91` (credential chain)
- **Flaw:** The plan verified only the OpenAPI schema and concluded the capability does not exist. The schema for `GET /tokens` declares zero parameters — but the route handler reads `req.query.expiry` and `req.query.scope` and passes both through. `GET /api/tokens?expiry=1y` mints a one-year token. The rejected design was implementable; a locked decision (store the user's *password* in a plaintext 0600 file) was justified in part by its impossibility.
- **Failure scenario:** The plan ships a credential store that keeps a reusable **NPM admin password** in plaintext at `~/.config/npmctl/credentials.json` on a box where an AI agent has Bash access (`phase-04:53` `allowed-tools: Bash(npmctl:*)`). Any file read — an agent debugging, a backup, a synced dotfiles repo — yields permanent full admin credentials for a production instance, when a scoped 1-year token (revocable by rotating the JWT signing key, and useless for the NPM web UI login) was available. The plan's own defence (`phase-01:91`, "same posture as `gh`, `docker login`") is inexact: `gh` stores an OAuth **token**, not the user's account password.
- **Evidence:**
  - `backend/schema/paths/tokens/get.json` → `{"operationId":"refreshToken", "security":[{"bearerAuth":[]}], "responses":{…}}` — **no `parameters` key at all**.
  - `backend/routes/tokens.js` → `.get(jwtdecode(), async (req,res,next) => { const data = await internalToken.getFreshToken(res.locals.access, { expiry: typeof req.query.expiry !== "undefined" ? req.query.expiry : null, scope: typeof req.query.scope !== "undefined" ? req.query.scope : null }); … })` — unvalidated, undocumented, functional.
  - `backend/internal/token.js` `getFreshToken()` → `parseDatePeriod(thisData.expiry)`; `backend/lib/helpers.js` `parseDatePeriod` accepts `/^([0-9]+)(y|Q|M|w|d|h|m|s|ms)$/` — so `1y`, `90d`, `26w` all valid.
  - Note the corollary: because this is undocumented and unvalidated, `schema check` (`phase-03:59`) can never detect it being removed. Treat it as best-effort with a fallback.
- **Suggested fix:** Delete the false claim from `plan.md:58` and `phase-01:74`. Re-open D7 with the real option set: (a) default profile stores a long-lived token obtained via `GET /tokens?expiry=…`, password never persisted; (b) `--store-password` as opt-in for 2FA-free unattended use. Add a `npmctl auth token --expiry 1y` command. Flag to the user that this reverses a locked decision and needs their sign-off (per `review-audit-self-decision.md`) — but the decision was made on a false premise, which is new evidence.

## Finding 5: `audit-log --limit` / `--offset` do not exist; the endpoint is hard-capped at 100 rows. This is exactly the bug class fixtures-only testing cannot catch.

- **Severity:** High
- **Location:** `phase-03-admin-resources.md:78` ("Read-only, paginated. Support `--limit`, `--offset`, `--expand user`"), `phase-03:93` (impl step 3 "list with pagination + expand"), `phase-03:107` (success criterion `audit-log list --limit 10 --expand user` works)
- **Flaw:** Neither `limit` nor `offset` exists. The route validates its query with `additionalProperties: false` against exactly two properties — `expand` and `query` — and the internal query hardcodes `.limit(100)`. `--offset` is not merely undocumented, it is **unimplementable**. The plan also misses `query`, the one search parameter that actually exists, while calling this endpoint the phase's "one admin endpoint with genuine agent value".
- **Failure scenario:** Implementer writes `testdata/audit-log-list.json`, writes `--limit`/`--offset` into flags and the request URL, and the fixture test passes because the fixture is whatever the implementer decided the response looks like. Shipped. In production the flags are silently ignored (or 400 if sent inside the validated object), and `npmctl audit-log list --offset 100` returns the same newest 100 rows as `--offset 0`. An agent asked "what changed last month on a busy instance?" gets confidently wrong output with no error. This is the concrete answer to the D9 question: `schema check` compares **paths and methods and request-body required fields** (`phase-03:69`) — it does not compare query parameters, does not compare response semantics, and here the parameters are absent from the schema in the first place, so a diff against the vendored schema reports zero drift. Fixtures + `schema check` cannot catch invented request parameters, server-side coercion (Finding 2), hardcoded server limits, or undocumented working parameters (Finding 4). `plan.md:70` rating R5 "Med (accepted)" understates this.
- **Evidence:**
  - `backend/schema/paths/audit-log/get.json` → no `parameters` key.
  - `backend/routes/audit-log.js` GET `/` → `validator({ additionalProperties: false, properties: { expand: {$ref: "common#/properties/expand"}, query: {$ref: "common#/properties/query"} } }, { expand: …split(","), query: … })`.
  - `backend/internal/audit-log.js` `getAll()` → `auditLogModel.query().orderBy("created_on","DESC").orderBy("id","DESC").limit(100).allowGraph("[user]")`.
  - Also: the `query` search is `this.where(castJsonIfNeed("meta"), "like", \`%${searchQuery}\`)` — **no trailing `%`**, so it is a suffix match on the serialised meta, not a substring search. Do not document it as "search".
- **Suggested fix:** Replace `--limit/--offset` with `--query <text>` and `--expand user`, and document "returns the 100 most recent entries; the API provides no pagination". Change `phase-03:107` accordingly. Add to `plan.md` risks: "invented request parameters are invisible to `schema check`" — mitigate by requiring every flag the CLI adds to cite the schema `parameters` entry or the route handler that reads it.

## Finding 6: `settings` is a one-setting closed enum; `oauth-auth` does not exist, and the free-form `--value-json` design is built on a schema that rejects free-form input

- **Severity:** High
- **Location:** `phase-03:57` ("`settings set` — free-form values"), `phase-03:44` (endpoint map), `phase-03:92` (impl step 2), `phase-03:104` (success criterion)
- **Flaw:** `phase-03:57` claims "Settings values are typed per setting ID (`default-site`, `oauth-auth`, …) with heterogeneous shapes. Do not model each." In v2.15.1 there is exactly **one** setting ID and its value is a 5-member string enum. `oauth-auth` is fabricated. The plan then designs around its own fabrication: an unvalidated `--value-json` passthrough for a body that is `additionalProperties: false`, and a runtime existence check that is strictly weaker than the compile-time-knowable enum.
- **Failure scenario:** (a) `npmctl settings set default-site --value-json '{"mode":"html"}'` → the ID check passes (`default-site` exists), the request is sent, HTTP 400 "must NOT have additional properties" — a failure the CLI had every fact needed to prevent, surfaced to an agent as a generic exit 6. (b) Worse, the actual use case is broken: setting the default site to custom HTML requires `meta.html`, and `--value` / `--value-json` as specified addresses only `value`. (c) Worst, `meta` is a required part of this operation, which contradicts the plan's global rule at `plan.md:60` / `phase-02:68` ("Everywhere else the R1 rule holds: omit it") — the plan lists exactly one exception (`cert create`); this is an unlisted second one. An implementer following the R1 rule literally will strip `meta` and make `settings set default-site html` silently store nothing.
- **Evidence:**
  - `backend/schema/paths/settings/settingID/put.json` → path param `settingID`: `{"type":"string","minLength":1,"enum":["default-site"]}`; body: `{"additionalProperties":false,"minProperties":1,"properties":{"value":{"type":"string","enum":["congratulations","404","444","redirect","html"]},"meta":{"additionalProperties":false,"properties":{"redirect":{"type":"string"},"html":{"type":"string"}}}}}`; `security: [{bearerAuth: ["admin"]}]`.
  - No `oauth-auth` path, component, or enum member exists anywhere in `backend/schema/` at `v2.15.1`.
- **Suggested fix:** Model it. `npmctl settings set default-site <congratulations|404|444|redirect|html> [--redirect URL] [--html FILE]` — one command, closed enum, validated client-side, exit 2 on invalid input, no network round-trip needed for validation. Delete `--value-json`. Add `settings` to the documented exceptions to the meta-omission rule at `plan.md:60`.

## Finding 7: `cert upload` / `cert validate` are `multipart/form-data` and `cert download` returns `application/zip` — none of it fits the JSON client, and `--dry-run` will print a PEM private key to stdout

- **Severity:** High
- **Location:** `phase-02:44–45` (endpoint map), `phase-02:103` (impl step 5, "all 9 operations"), `phase-02:94` (only change to `client.go` is "per-operation timeout override"), `phase-01:107–117` (`Op.Body any`), `phase-01:123` (dry-run "print `METHOD /path` + pretty body"), `phase-01:218` (success criterion: credentials absent from `-v`)
- **Flaw:** Two of the nine certificate operations are not JSON. The plan's endpoint map lists them as ordinary POSTs, `client.go`'s only stated modification is a timeout knob, and no multipart writer, boundary handling, or `Content-Type` negotiation is budgeted anywhere. Separately and more seriously: the plan's credential-redaction scope is "passwords and tokens". A TLS **private key** is neither, so it flows through `Op.Body` into the dry-run printer and the verbose logger.
- **Failure scenario:** `npmctl cert upload 7 --key server.key --cert server.crt --dry-run` — per `phase-01:123` the Guard prints the pretty body before returning. The unencrypted private key is written to stdout, into the agent's transcript, into the terminal scrollback, and (with `-v`) into any log file, while `phase-01:218`'s grep test passes because it only greps for the password and the JWT. An agent then relays the dry-run output back to the user "so they can review what will change" (`phase-04:63`), putting the private key into a model context and possibly a chat log. Second scenario: the implementer discovers the multipart requirement mid-P2 (the "1-2 days"/"2-3 days" estimate has no room for it) and reaches for the shortcut of POSTing JSON, which `express-fileupload` will not populate — `req.files` is undefined and the upload fails with a 500 carrying a stack trace (see Finding 8b).
- **Evidence:**
  - `backend/schema/paths/nginx/certificates/certID/upload/post.json` and `…/certificates/validate/post.json` → `"requestBody": {"$ref": "…/common.json#/properties/certificate_files"}`.
  - `backend/schema/common.json` `properties.certificate_files.content` has exactly one key: `"multipart/form-data"`, schema `required: ["certificate","certificate_key"]`, optional `intermediate_certificate`.
  - `backend/app.js` → `app.use(fileUpload());` — the server reads these from multipart, not from `bodyParser.json()`.
  - `backend/schema/paths/nginx/certificates/certID/download/get.json` → response content type `application/zip`, `schema: {"type":"string","format":"binary"}` (so `phase-02:81`'s "returns a file" is right, but it is specifically a zip archive; `--output-dir` needs a `.zip` name).
- **Suggested fix:** Add to `phase-02`: a `multipart` request path in `client.go` (explicit, listed in "Related Code Files" as a `client.go` modification), and a redaction contract that treats `Op.Body` as **secret by default** for the certificate group — dry-run prints field names and byte lengths for `certificate`, `certificate_key`, `intermediate_certificate`, never contents. Extend `phase-01:218` to assert a PEM `BEGIN … PRIVATE KEY` block never appears in stdout or verbose output. Note `download` writes a `.zip`.

## Finding 8: Three cross-cutting P1 mechanics are specified against the wrong signal or an incomplete model of NPM's responses

- **Severity:** Medium
- **Location:** (a) `phase-01:197` + `phase-01:126`; (b) `phase-01:192` + `phase-01:128–139`; (c) `phase-01:191` + `phase-01:137`
- **Flaw and failure scenarios:**

  **(a) TTY detection gates the confirmation prompt on the wrong stream.** `phase-01:197` specifies one TTY signal — `os.Stdout.Stat()` char-device check — and `phase-01:126` uses the same signal to decide whether to *prompt interactively*. Output format legitimately depends on stdout; **interactivity depends on stdin.** Concrete failures: `npmctl host rm 12 | tee audit.log` from a live terminal → stdout is a pipe → Guard takes the `!TTY` branch and exits 3, even though a human is present and could confirm; the user's fix is to pass `--yes`, which trains exactly the habit `phase-04:69` warns against. Inverse: `npmctl host rm 12 < /dev/null` on a terminal → stdout is a char device → Guard prompts, reads EOF immediately, and the plan does not say whether EOF means abort (it must). Docker `-t` without `-i` reproduces the inverse case exactly. *Fix:* prompt only when `os.Stdin` **and** `os.Stderr` are terminals; select output format from `os.Stdout`; treat EOF on the prompt as refusal (exit 3), never as consent.

  **(b) The error-body model is incomplete, and the cert path leaks stack traces.** `phase-01:192` parses `{"error":{"code","message"}}`. Verified in `backend/app.js`: the payload is `{error:{code: err.status||500, message: err.public ? err.message : "Internal Error"}}`, **plus** an optional `error.message_i18n`, **plus** `payload.debug = {stack, previous}` emitted whenever `isDebugMode() || (req.baseUrl + req.path).includes("nginx/certificates")` — i.e. **always for every certificate endpoint, in production**. Two consequences: any non-`public` error (the interesting ones) arrives as `"Internal Error"` with status 500, so `phase-04:106`'s marquee troubleshooting recipes ("cert renewal failure", "502 diagnosis") will render "Internal Error" unless npmctl reads `debug.previous`/`debug.stack`, where the certbot output actually lives; and if npmctl echoes unparsed bodies or dumps them under `-v`, it prints upstream Node stack traces and container filesystem paths. *Fix:* parse `message_i18n` and `debug`; surface `debug.previous` on cert failures behind `-v` only; never echo `debug.stack` by default. Note `err.status||500` also means the exit-code table has no mapping for 403 (below).

  **(c) `strict routing` is enabled, so a trailing slash 404s — and the plan maps 404 to "not found".** `backend/app.js` sets `app.enable("strict routing")` and every router is constructed `{caseSensitive: true, strict: true}`. `phase-01:191` says only "base URL join". A profile URL of `https://npm.example.com/` naively joined produces `//api/nginx/proxy-hosts` and any accidental trailing slash produces a 404 → the plan's exit 5 "not found". The user is told "proxy host not found" when the real fault is a trailing slash in `config.yaml`. *Fix:* normalise the profile URL at load (strip trailing slashes, reject paths), never emit trailing slashes, and add a unit test for `https://host/`, `https://host:81/`, and `https://host/npm/` inputs.

- **Evidence:** `backend/app.js` (error handler, `app.enable("strict routing")`), all `backend/routes/*.js` router constructors, plus the cited plan lines.

## Finding 9: "All 44 endpoints" is a miscount, and the acceptance criterion that checks it cannot fail

- **Severity:** Medium
- **Location:** `plan.md:19`, `plan.md:44` (D3), `plan.md:77` (AC2), `phase-03:14`, `phase-03:103` ("All 44 endpoints now reachable — checklist verified against the vendored schema's **path list**")
- **Flaw:** 44 is the number of **path keys**; there are **68 operations**. The plan's phase command maps do cover most operations, so this is not a wholesale coverage gap — but `phase-03:103` validates coverage against the *path list*, which will read 44/44 while operation coverage is unverified. Two concrete gaps survive that criterion: (i) `GET /` (`operationId: health`) appears in no command map in any phase; (ii) per-operation authorization scopes are never modeled and there is no exit code for 403, so "reachable" is untested for roughly a third of the surface.
- **Failure scenario:** P3 is marked complete with 44/44 green. In production a non-admin operator runs `npmctl audit-log list` and `npmctl settings set` and `npmctl user login-as` — all require scope `admin` — and gets permission errors mapped to exit **6 ("API error")**, indistinguishable from a transient 5xx. `SKILL.md` rule 6 (`phase-04:66`) tells the agent that only exit 3 is a refusal, so the agent treats a permanent 403 as retryable and hammers it. Separately, on a freshly deployed NPM the operator's first `npmctl auth login` fails with a confusing auth error; `GET /api/` returns `{"status":"OK","setup":false,…}` and would have explained it in one call, but nothing in the plan ever calls it.
- **Evidence:**
  - `swagger.json` at `v2.15.1`: `len(paths) == 44`, and enumerating `(path, method)` pairs yields **68** operations.
  - `backend/schema/paths/get.json` → `{"operationId":"health", …, "value":{"status":"OK","setup":true,"version":{…}}}` — not in any phase's endpoint map.

## Finding 10: `schema check` is circular and will report drift on every run; producing its own fixture violates D9

- **Severity:** Medium
- **Location:** `phase-03:59–74` ("`schema check` — R5/R7 mitigation"), `phase-03:98` (impl step 8), `phase-03:108–109` (success criteria), against `plan.md:50` (D9) and `plan.md:81` (AC6: "hermetic: no network, no Docker")
- **Flaw:** Three defects. (i) The live `/api/schema` response is **mutated per request** — `info.version` is overwritten with the running package version and `servers[0].url` is derived from the request's `Origin` header — so a naive structural diff against a vendored copy reports drift on every single invocation, and `servers[0].url` varies with the client's own headers and reverse-proxy setup. A drift detector that always fires is a drift detector nobody reads. (ii) `phase-03:74` and `phase-03:98` require vendoring the **dereferenced** form, obtainable only "from a live instance" — so building the hermetic test fixture requires the live NPM that D9 forbids, and `schema check --from-file` in CI then validates a fixture that was hand-captured once and can never be regenerated hermetically. (iii) The diff covers "paths added/removed, methods added/removed, required-field changes" — none of which would have caught Findings 2, 4, 5, or 6. Query parameters, response shapes, enum narrowing, `additionalProperties`, and `minProperties` are all outside its scope, and undocumented-but-working behaviour is outside the schema entirely.
- **Failure scenario:** `schema check` ships. First real run against production prints `~ info.version: 2.x.x → 2.15.1` and `~ servers[0].url: … → https://npm.example.com/api`, exits 1. R7's mitigation is now noise; the operator adds it to an ignore list or stops running it, and the next real drift — a narrowed enum, a new required field on `POST /nginx/certificates` — lands silently.
- **Evidence:**
  - `backend/routes/schema.js` → `const swaggerJSON = await getCompiledSchema(); … let origin = \`${proto}://${req.hostname}\`; if (req.headers.origin) { origin = req.headers.origin; } swaggerJSON.info.version = PACKAGE.version; swaggerJSON.servers[0].url = \`${origin}/api\`;`
  - `backend/schema/index.js` → `$RefParser.dereference(…, {mutateInputSchema: false})`, memoised. (The plan's claim at `phase-03:74` that `/api/schema` is dereferenced is **correct** — one of the few API claims that holds.)
  - The in-repo `swagger.json` is 8 KB with external `$ref`s, as `phase-03:74` states, confirming the apples-to-apples problem is real.
- **Suggested fix:** (a) Normalise before diffing — drop `info.version`, `servers`, and all `example`/`examples` nodes; document the ignore list in the phase file. (b) Resolve the D9 contradiction explicitly: either dereference the vendored `$ref` schema in Go at test time (a small resolver — the `$ref`s are relative file paths, and this keeps the fixture regenerable and hermetic), or state plainly that the fixture is a one-time manual capture and that `schema check`'s own fixture is untestable. (c) Extend the differ to query `parameters`, `enum` values, `additionalProperties`, and `minProperties`, since Findings 2/5/6 all live in exactly those fields. (d) Downgrade the claim at `phase-03:72` ("Recovers most of what integration tests would have caught") — it recovers path/method drift and nothing else.

## Secondary assumptions checked — not written up as full findings

1. **`plan.md:34` "P2/P3 independent of each other after P1" — false.** `phase-02:95` modifies `internal/cli/root.go`; `phase-03:86` modifies `internal/cli/root.go`; `phase-03:87` modifies `internal/cli/guard.go`. `phase-02:99` (impl step 1) proposes extracting the P1 CRUD shape into a shared generic helper — a refactor of the exact code P3's user CRUD would build on. Per `orchestration-protocol.md` ("Avoid parallel edits to the same file"), these cannot run in parallel as written. Either sequence them, or move the `root.go` command-group registry to a per-group `init()` pattern first.
2. **Effort estimates are not credible as scoped.** P1 at 2–3 days: 17 files, credential chain with three backends, session refresh, a write gate with a bypass-detection test, four output renderers, plus the 2FA branch — and Findings 2, 3, and 8 all add unbudgeted P1 work. P3 at 1–2 days includes `schema check` (self-estimated ~120 LOC, `phase-03:72`, which Finding 10 shows is under-scoped), nine user subcommands, and 2FA passthrough. Expect ~2x.
3. **`phase-04:91` go-keyring / `CGO_ENABLED=0` — unverified and correctly flagged as such.** The note "verify the static build works on each target before claiming it" is the right posture. But `phase-01:89` already concedes keyring is unavailable on headless Linux (no D-Bus), which means the *practical* backend on the most likely agent host (a Linux container) is always the plaintext file — see Finding 4. `linux/arm64` and `windows/amd64` keyring behaviour is asserted nowhere and cannot be verified from macOS; make it a release-blocking manual check, not a success-criteria checkbox.
4. **`DELETE` and `enable`/`disable` return a bare JSON `true`, not an object.** `backend/schema/paths/nginx/proxy-hosts/hostID/delete.json` → `"schema": {"type": "boolean"}`, example `true`. The `Render(any)` table renderer (`phase-01:197`) and the "JSON when piped" contract (`plan.md:78`) must handle scalar top-level values; a table renderer that reflects over struct fields will panic or emit an empty table. Cheap to fix, easy to miss.
5. **`certificate_id` accepts the magic string `"new"`.** `backend/schema/common.json` → `certificate_id: {anyOf: [{type:"integer",minimum:0},{type:"string",pattern:"^new$"}]}`, and `internal/proxy-host.js` branches on `thisData.certificate_id === "new"` to call `createQuickCertificate`. This is the only single-call "create host with a new LE cert" path, it is the one place proxy-host `meta` is actually read, and it inherits R2's 30–90s ACME block on a `POST`/`PUT` to a *host* endpoint (so the 180s timeout rule at `phase-02:26` must extend to host create/update when `certificate_id=new`). The plan mentions none of this. A typed `SetCertificateID(int)` builder cannot express it.
6. **Ajv runs with `coerceTypes: true`** (`backend/lib/validator/api.js`). Type mismatches are silently coerced rather than rejected, so fixture tests that assert "the server would reject this" are unfalsifiable, and `"8080"` vs `8080` bugs will not surface until a value coerces wrongly.
